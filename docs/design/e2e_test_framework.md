以“已有能力可以表达的新配置组合”为例，目前与调整后的维护路径如下：

| 工作 | 当前 | 调整后 |
| --- | --- | --- |
| 定义组合 | 模型 `test_*.py` 选择 ID、设备和命令；`runner.configure_scenario` 再按 ID 配置布局和模式 | 模型 `cases.py` 声明配置并暴露 ID；既有参数化入口读取 ID |
| 选择任务与检查 | 按需要修改 runner 中的模型分支、评测选择及证据条件 | Case 选用既有任务与检查，公共模块改动必须为空 |
| 安排执行 | 必要的 CI node ID 选择及资源配置 | 同样由 CI 选择和分配资源；不改场景验收标准 |

新增任务、检查、部署协议或 connector 能力时，才扩展对应模块并附上验证，不能将能力扩展伪装成纯配置新增。

## 1. 目标与范围

本次调整要让维护者能够在模型目录中看清一个场景的完整含义，并使用公共能力新增和维护用例：

- 已有能力可以表达的新配置组合，只修改模型场景声明、ID 清单及必要的 CI 选择和文档；公共模块的增量改动必须为空，以新增组合前后的 diff 验收。
- 新增请求任务、检查、部署协议或 connector 能力，才允许扩展对应公共模块，并提供与该能力相应的验证。独立框架缺陷作为明确的修复评审，不归入纯配置新增。
- 仍需要的场景保留有效覆盖；确认淘汰的行为连同专用测试和辅助代码一起删除。
- CI 与本地使用同一用例定义，CI 负责选择用例、提供资源和安排频率。

E2E 的范围是启动真实服务、运行真实负载、验证结果并清理本次创建的资源。算子测试、性能平台、PD/proxy 部署工具不因本次整理自动成为统一框架的用例。现有这些工具仍按其实际用途维护。

调整覆盖现有 GPU/NPU、baseline/AFD、不同 A/F 布局、graph/DBO、模型专用验收和 multi-pod 入口；迁移分批进行。本文不新增模型支持承诺，不降低当前验收强度，也不建设新的调度平台。

## 2. 当前需要解决的问题

AFD 已有公共 runner、评测工具和进程管理能力，主要维护成本来自场景信息分散。

| 当前事实 | 代码位置 | 调整方向 |
| --- | --- | --- |
| 模型入口既列场景，又分设备、拼命令和调整评测参数 | [DeepSeek-V2-Lite 入口](../../tests/e2e/models/deepseek_v2_lite/test_deepseek_v2_lite.py) | 场景含义集中到模型的场景模块 |
| 场景名决定拓扑、TP、graph、DBO、后端限制和模型配置 | [runner.py](../../tests/e2e/runner.py) 的 `configure_scenario`、`validate_topology` | 公共代码使用明确的配置和协议要求 |
| 通用 runner 导入 DSV4 配置及评测函数 | 同文件的导入、`build_vllm_command` 和 `main` | 模型模块向公共流程提供配置和函数 |
| DSV4 GPU 的两轮并发及 GSM8K 三阶段评测直接在 `main` 中组织，不经过 `run_scenario_evaluation` | [runner.py](../../tests/e2e/runner.py) 的 `main`，基线第 227–249 行 | 模型声明阶段和跨窗口要求，公共 runner 按声明执行 |
| 清理策略、超时及评测选择还依赖具体场景名 | 同文件的 `uses_npu_async_process_cleanup`、`run_scenario_evaluation` | 明确服务生命周期和场景验收的归属 |
| MRV2、FFN graph、DSpark 各有证据处理流程 | [MRV2](../../tests/e2e/mrv2_evidence.py)、[FFN graph](../../tests/e2e/models/deepseek_v4_flash/ffn_graph.py)、[DSpark](../../tests/e2e/models/deepseek_v4_flash/dspark_eager.py) | 相同流程复用，具有不同证明意义的探针和断言分别保留 |

这些是已观察到的组织问题。它们不能直接证明某个现有场景错误，也不能单独作为删除用例的依据。

当前单机流程如下；其中的分支均由 `runner.py` 组织：

```text
模型 test_*.py：选择场景、准备资产、拼 runner 命令
    → tests/conftest.py::run_runner()：启动子进程
    → runner.main()：按场景名配置、校验、准备探针、选择 A/F 启动顺序
    → 启动服务并等待就绪
    → 分支：DSV4 GPU → 两轮并发及窗口检查 → 跨轮检查 → GSM8K 及窗口检查
            其他场景 → evaluation 窗口 → run_scenario_evaluation()
    → 存活检查 → 按场景选择清理策略 → 报告结果
```

## 3. 目标架构与代码归属

### 3.1 模块协作图

下图表达模块协作，不表达执行先后；每条连线标明调用或参数输入。除 `tests/conftest.py` 外，路径均相对于 `tests/e2e/`。星号表示拟新增文件。

```text
pytest 进程
models/<model>/test_*.py
    └── 调用 ──▶ tests/conftest.py::run_runner()
                       │
                       └── 启动独立子进程
                                  │
                                  ▼
runner 子进程
models/<model>/cases.py*
    │
    │ 向公共入口提供场景构建函数
    ▼
runner.py
    ├── 读取 ──▶ environment.py
    ├── 调用 ──▶ 注入的构建函数，取得 Case
    ├── 调用 ──▶ deployment.py*
    │               └── 使用 process_utils.py、cancellation.py
    ├── 调用 ──▶ Case 指定的任务
    │               └── 例如 accuracy/gsm8k.py、模型专用任务
    └── 调用 ──▶ Case 指定的检查
                    └── 例如 checks/mrv2.py*、模型专用检查

case.py* 定义这些模块交换的场景结构。
worker 侧探针运行在被测服务中，通过 RPC、日志等提供证据。
```

公共 runner 调用模型提供的构建函数，不反向导入某个模型配置模块。任务和检查通过 Case 传入，不由公共 runner 根据模型名或 case ID 选择。

### 3.2 模块职责

| 模块 | 状态 | 职责与边界 |
| --- | --- | --- |
| `case.py` | 新增 | 定义场景、部署和评测阶段需要交换的数据结构；不启动服务、不导入具体模型 |
| `models/<model>/cases.py` | 新增 | 提供可安全导入的稳定 ID 清单；仅在 runner 子进程中构建完整 Case，作为该模型的运行入口 |
| `models/<model>/test_*.py` | 调整 | 收集时只读 ID 并参数化，执行时调用子进程辅助函数；保留已有 pytest node ID |
| `runner.py` | 精简 | 组织检查准备、部署、评测阶段、存活检查和退出；传播失败 |
| `environment.py` | 扩展 | 读取运行参数，解析路径、设备、地址、端口和可执行程序；不定义场景的验收标准 |
| `deployment.py` | 新增 | 校验拓扑、绑定资源、构造角色命令；按 connector 协议表决定启动顺序，执行 `cleanup_profile`，等待就绪、检查存活并回收服务 |
| `accuracy/gsm8k.py` | 扩展 | 执行 GSM8K、解析结果、验证退出状态、样本数和精度；接收明确的评测配置 |
| `checks/mrv2.py` | 新增 | 提取当前主机侧的探针配置、窗口控制、证据获取和 graph/DBO/Hash 检查 |
| `mrv2_evidence.py` | 保留 | worker 侧 MRV2 探针；不与主机侧控制代码混为一个运行模块 |
| 模型专用配置、任务、检查与探针 | 按实际需要保留 | 模型特有逻辑留在模型目录；不要求所有模型创建相同的一组文件 |
| `multi_pod/` | 保留并逐步接入 | 负责布局、地址发现、barrier 和失败通知；通过 deployment 的本地执行器管理各 pod 服务 |
| `process_utils.py`、`cancellation.py` | 保留 | 底层进程组终止、回收和取消机制，不承载模型判断 |
| `tests/conftest.py` | 保留 | 管理 runner 子进程及信号转发；与部署模块管理被测服务的职责区分 |

服务的启动与释放统一归部署模块，不再设置一个与它重叠的生命周期模块。multi-pod 协调层复用现有协调实现，每个 pod 的部署执行器唯一拥有本地进程，只回收自己创建的资源。现有本地 executor 可以作为 deployment 的适配实现；协调层不再独立执行第二套清理，清理策略只有 `cleanup_profile` 一个来源。

## 4. 场景、环境和模型配置

### 4.1 Case 应当表达什么

Case 至少包含以下信息，具体类型名由试点实现确定：

| 内容 | 含义 |
| --- | --- |
| 稳定 ID 与覆盖目的 | 哪个行为需要这个用例；ID 在相应模型和后端入口内保持稳定 |
| 适用模型和后端 | 模型固定要求、量化和 tokenizer 等必要条件 |
| 部署描述 | baseline 或 AFD、各角色 DP/TP 等布局、connector 及其配置 |
| 清理描述 | Deployment 显式声明 `cleanup_profile` 及关闭等待预算；默认 `strict`，限定例外见 §5.5 |
| 各角色运行模式 | eager、graph、DBO 等实际设置；允许 A/F 模式不同 |
| 有序评测阶段 | 每阶段的名称、任务参数、结果要求和必要执行证据 |
| 限制和验收范围 | 资源需求、已有平台限制，以及仅 smoke、结果精度或路径验收等结论边界 |

当前 AFD 布局中，每角色设备需求由其 DP/TP 等配置确定，实际校验沿用后端和 connector 的有效规则。不要同时维护语义不清的“角色数量”和“总 rank 数”两套来源。

场景名称只用于选择和报告。公共代码允许基于后端、角色、部署形态和 connector 协议分支，避免根据具体 case ID 推断这些信息。

角色启动顺序归 `deployment.py` 的 connector 协议表，Case 只选择 connector，不提供按场景覆盖启动顺序的字段。迁移现有协议时保留以下顺序：

| 部署 / connector | 角色启动顺序 |
| --- | --- |
| native baseline | baseline |
| GPU `P2pNcclAFDConnector`、`DeepEPM2NAFDConnector`；NPU `CAMP2pAFDConnector` | FFN → Attention |
| NPU `CAMAsyncAFDConnector` | Attention → FFN |

这里的先后指进程启动，不是要求第一个角色先完成整个服务的就绪。单机双方启动后等待公开服务就绪；multi-pod 复用同一协议决策，并由现有协调层保留第一类角色启动后的跨 pod barrier。不能在各入口重复维护一份顺序判断。

### 4.2 环境提供什么

环境提供实际模型路径、分配到的设备、网络地址、端口、运行程序和输出目录。场景声明需要哪些资源及验收设置，环境解析后才能绑定实际值。

不同 NPU 硬件、同步/异步 connector 的环境参数按适用配置复用，保留必要差异。模型固定参数留在模型模块，跨场景相同的设置集中定义。

现有本地调试变量的优先级、样本数下限和并发要求需要显式迁移。CI 不通过环境变量暗中降低场景验收要求；最终生效配置应能从运行输出中确认。

Case 保存规范验收配置，运行记录同时保存最终生效配置及全部覆盖项。任务执行成功和取得固定场景验收资格分别记录：降低样本数、阈值、必需并发、检查强度或关闭要求的运行只能用于调试，不能作为迁移通过、覆盖资格或替代删除记录。增加样本等变更按场景明确允许的规则判断；更换路径、设备、地址和端口，在满足模型及资源要求时不改变资格。具体而言，128 题场景的 24 题调试运行不能取得该场景的迁移资格。

启动参数按下表合成，不能依赖 CLI 追加顺序或最后一个值覆盖前值。角色/通用额外参数和配置文件同样受该归属约束；不兼容冲突在启动前失败，允许的覆盖须有明确规则，并记录实际被测值。

| 参数 | 唯一语义来源 | 合成与覆盖规则 |
| --- | --- | --- |
| 拓扑、connector、各角色 graph/DBO 模式及 `cleanup_profile` | Case 的部署描述 | deployment 据此生成命令；环境和额外 CLI 不可暗中改写 |
| 模型固定参数、量化、tokenizer | 模型 profile 与显式场景变体 | 环境只绑定合格 checkpoint；变体必须在场景中声明 |
| worker extension 与探针启动参数 | 所选检查的合并需求，结合模型所需 extension | 同一探针只注入一次；不兼容的类或配置在启动前报错，不能后写覆盖 |
| 实际设备、地址、端口与程序 | 解析后的环境 | 绑定场景要求，不改变布局和验收范围 |
| 请求、生成参数、样本数、阈值与必要证据 | Case 的阶段及任务配置 | 只按显式规则覆盖；减弱的调试配置不能取得固定场景资格 |

### 4.3 pytest 与 runner 如何传递场景

保留独立子进程边界，推荐以下入口关系：

1. 模型模块分别提供可安全导入的不可变 ID 清单与 `build_case(case_id, environment)`；收集入口不调用构建函数。
2. pytest 收集阶段只根据明确的后端参数读取 ID 并参数化，不解析 checkpoint 路径、不探测量化、不下载资产、不初始化设备、不启动服务。
3. `run_runner` 启动对应模型场景模块，仅传递 ID、环境和必要运行选项。
4. 模型模块调用公共 CLI 入口，并注入 `build_case`；公共入口读取环境后调用它。
5. 构建完成的 Case 在子进程内部交给 `run_case` 执行。

因此不需要序列化带 Python 函数的 Case，也不需要在通用 runner 中维护一个导入所有模型的注册表。解析实际 checkpoint 路径、读取模型配置和探测量化等工作仅在 runner 子进程中进行；所需资产也在执行阶段准备。

收集安全要求覆盖整个导入链。ID 清单所在模块及其顶层导入不能间接执行上述工作；仅将 `build_case()` 的调用移到子进程还不够。迁移时需检查模型入口及共享 `conftest.py` 的导入路径。

不能仅以“运行时包未安装”的收集结果证明全部导入路径安全。当前共享 `conftest.py` 在发现 vLLM-Ascend 后会导入 `vllm_ascend.ops`；迁移需审查包存在时的分支，并在对应环境核对收集时没有加载设备运行时、初始化设备或读取 checkpoint。导入或 ABI 问题不得通过屏蔽错误掩盖。

该入口是目标设计。旧命令、multi-pod 和专用脚本仍有现存调用者，必须随对应场景一起迁移并更新文档；不能仅移走函数就删除旧入口。

## 5. 执行、检查与失败处理

### 5.1 调用约定

建议使用少量明确的数据结构和普通 Python 函数。先约定必要输入、输出与资源归属，具体函数签名通过试点收敛。

| 调用 | 约定 |
| --- | --- |
| 模型的 `build_case` | 接收 ID 和已解析环境，返回完整 Case；不启动服务 |
| 公共的 `run_case` | 接收 Case 和环境，组织全过程；失败向外抛出，成功不能早于清理完成 |
| 部署上下文 | 进入时启动并等待服务；退出时回收。部分启动失败也必须清理已创建资源 |
| 任务函数 | 使用公开端点或明确支持的评测接口，执行真实负载并验证任务结果 |
| 路径检查 | 提供所需探针配置、窗口控制和证据判定；缺少必需证据时失败 |

Case 和模板保留配置，不持有跨用例复用的可变计数、进程对象或探针状态。运行状态随本次执行创建并释放。

同一部署的 graph、DBO、Hash 等检查共享探针时，只准备一次、对每个阶段采样一次。公共执行流程统一组织 reset、开启和结束窗口；探针产生证据，检查只解释证据，不各自重置计数或重开窗口。启动要求不兼容时，在启动前失败。

每阶段保存独立且完成后不再被后续采样改写的证据快照，关联本次运行、部署、阶段及角色/rank。多项检查消费同一快照；跨阶段检查读取已完成阶段的快照。前一窗口、其他部署或 capture/profile 的记录不能充当当前真实请求证据，不需要为此引入通用探针注册框架。

### 5.2 执行顺序

以下是运行步骤，和前面的模块协作图分开理解：

```text
解析环境、构建并校验 Case
    ↓
准备所选检查需要的探针、通信材料和角色启动参数
    ↓
deployment 启动服务并等待就绪
    ↓
评测前检查服务存活
    ↓
逐阶段执行：
    开始本阶段观测窗口
      → 执行请求任务并验证结果
      → 收集和检查本阶段证据
      → 执行该阶段需要的跨窗口检查
    ↓
评测后检查服务存活
    ↓
deployment 关闭服务并确认资源回收
    ↓
释放探针通信材料、临时文件和其他本次资源
    ↓
报告成功
```

任一步骤失败或取消，都进入资源清理路径。保留任务或证据失败的原因，同时报告清理失败；不得通过清理过程覆盖原始问题，也不得把清理失败转成成功。

### 5.3 探针必须在服务启动前准备

当前 MRV2 证据依赖 worker extension、角色环境和 marker 文件。检查不能只在请求结束后运行一个断言函数：

- 启动前，根据所选检查准备本次运行专属的探针配置和通信材料。
- 命令构造时注入对应 worker extension 和角色参数。
- 请求前重置、开启具名窗口，请求后获取并验证该窗口的证据。
- 同一探针服务多个检查时复用一次配置；服务退出后再释放它使用的通信材料。

探针只在相应验收需要时加载，保留当前 pure eager、普通 baseline 等场景的既有行为。主机控制与 worker 观测之间的协议维持明确边界，不为测试修改生产数据面。

### 5.4 结果检查与路径检查

任务自身验证响应或精度。例如 GSM8K 的退出状态、结果完整性、样本数、NaN 和精度阈值由任务模块处理，不拆成多个通用插件。

独立路径检查用于跨任务复用 graph、DBO、Hash 等执行证据：

- 保留现有参与角色、rank、真实 token、布局和窗口要求。
- dummy、profile、capture 或空的第二个 microbatch 不能冒充真实请求执行。
- 必需检查未执行、证据为空、rank 缺失或窗口不匹配均失败。
- 跨阶段检查可以读取前面阶段的证据，并在进入下一阶段前完成。

模型专用 FFN graph 与 DSpark 探针证明的内容不同，只有语义相同的代码才合并。Case 需要准确声明验收范围，不能把仅作 graph 配置对照的 baseline 或现有 smoke 自动宣传成完成了执行路径验收。

### 5.5 清理与取消

沿用现有进程归属、信号转发、超时和回收边界。普通 gate 的 SIGKILL 升级仍是失败。

清理策略由 Deployment 的 `cleanup_profile` 显式选择，公共 runner 和 deployment 不再根据场景名判断。适用范围如下：

| `cleanup_profile` | 适用范围与成功条件 |
| --- | --- |
| `strict`（默认） | 普通 gate 及要求优雅关闭的场景；服务需要 SIGKILL 升级或资源未回收均失败。#509 的 N12 使用此项 |
| `npu_async_cam_legacy` | 仅迁移现有 NPU async CAM eager 服务的 FFN 清理例外；保留本次运行与 FFN 角色标记、限定扫描、等待和存活检查。允许原有范围内的强制回收，不证明优雅关闭 |

模型 Case 显式选择已有例外，部署模块核对其 NPU / async CAM 适用条件；不能仅因 backend 或 connector 相同就自动启用。其他角色或其他清理错误不被该例外豁免。生效 profile 和关闭结果写入运行输出。

FFN graph 旧专用入口当前不验收优雅关闭，在使用者迁移前保留这一准确范围。迁入 N12 后必须通过 `strict` 验收，不能沿用旧入口的允许强制清理结果。

## 6. 代表性场景如何表达

### 6.1 DeepSeek-V2-Lite graph DP2

以下仅示意 Case 的结构，类名、常量和参数都是拟议接口：

```python
Case(
    id="afd-v2-graph-dp2",
    model=DEEPSEEK_V2_LITE,
    deployment=AFDDeployment(
        backend="gpu",
        connector="P2pNcclAFDConnector",
        cleanup_profile="strict",
        attention=Role(dp=2, tp=1, execution="full_decode_graph"),
        ffn=Role(dp=2, tp=1, execution="full_decode_graph"),
    ),
    phases=(
        Phase(
            name="gsm8k",
            task=GSM8K(settings=DEEPSEEK_SMOKE_GSM8K),
            # Check 还负责启动前准备并注入探针、提供观测窗口，最后才判定证据。
            checks=(MRV2Graph(roles=("attention", "ffn")),),
        ),
    ),
)
```

模型 profile 和评测配置集中定义；实际卡号、路径和端口不写在这份声明中。`DEEPSEEK_SMOKE_GSM8K` 在这个例子中代表该场景现有的 7 样本、8-shot、512 生成 token 上限和 0.25 smoke 阈值。

DBO 比较场景继续使用它们现有的 128 样本、12 并发和精度要求；不会因为共用 GSM8K 任务而套用这个 smoke 配置。完整阈值、下限与调试覆盖规则以现行契约为准。

### 6.2 DSV4 CUDA 多阶段场景

保持现有顺序与验收范围：

| 阶段 | 任务及结果 | 必需证据 |
| --- | --- | --- |
| `concurrent-1` | 第一轮并发请求和答案检查 | 本窗口适用的 graph/DBO 证据；AFD 场景的 A/F Hash 输入配对 |
| `concurrent-2` | 改变输入 ID，保持要求的请求形状 | 独立窗口证据、Hash 配对，以及与第一轮的输入新鲜性检查 |
| `gsm8k` | GSM8K 结果与精度检查 | 本窗口适用的 graph/DBO 证据，不强加并发窗口的有界 Hash 采样要求 |

跨轮新鲜性检查在第二轮结束后、GSM8K 开始前完成。不能用第一轮的累计计数替代第二轮或 GSM8K 的证据。

这类场景用于检验设计是否能表达真实的多阶段验收，不把它的请求细节写回通用 runner。

<a id="ffn-full-comparison"></a>

### 6.3 Async CAM FFN FULL 对照场景（issue #509）

[issue #509](https://github.com/vllm-project/afd-plugin/issues/509) 要求真实 NPU 上的 FFN FULL 回归，包括输出对照、长度和并发变化、capture/replay 证据，以及优雅关闭。它需要检验另一种执行关系：先部署 eager 参考，完成请求并释放服务，再以相同配置部署 FFN FULL，重放输入并比较输出。

一个测试应在自己的运行目录内完成两段执行，不依赖前一个 pytest 用例留下的参考文件或服务。因此，稳定的 pytest node ID 表示整体验收；一次部署的 Case 配置不强制与它一一对应。模型专用 pytest 入口可以顺序调用两次 runner，组合逻辑复用模型辅助函数，公共 runner 继续负责单次部署执行，不加入 FFN FULL 专用分支。

eager 和 FULL 使用独立子目录。参考必须来自本次测试，输入、生成参数、checkpoint 及影响结果的运行配置均有对应记录；eager 达到成功终态且完成规定关闭后，FULL 才能消费参考。除预先声明的 FFN 执行模式及必要探针差异，模型、拓扑、容量和请求配置一致；端口和目录等资源绑定分别记录。任一子运行失败、参考不完整、配置不符或输出比较失败，整个 pytest node ID 失败。公共 runner 返回单次结果与终态，模型辅助函数负责衔接，无须通用 `CompositeCase`。

capture 和 replay 的作用域分开：本次 FULL 部署应为全部要求的 FFN rank 建立预期图；每个选定请求窗口再证明真实请求带来的 replay 增量、实际 FULL 模式及无意外 fallback。后续窗口可以复用本次部署已 capture 的图，不能借用前一窗口累计 replay。eager 和 FULL 两段分别通过 `strict` 关闭与回收。具体窗口见[新增场景验收定义](e2e_case_matrix.md#new-case-acceptance)。

现有 [ffn_graph.py](../../tests/e2e/models/deepseek_v4_flash/ffn_graph.py) 已提供 Attention eager / FFN eager 或 FULL、多种输入长度、双 prompt batch、逐 rank capture/replay 证据和 FULL/eager token 对照。它是复用基础，尚不能代表 issue 的全部验收：

- 双 prompt batch 不等于多个 HTTP 客户端并发，现有不同输入的连续请求也没有专门检查同输入重复执行；负载需按原需求补齐。
- 当前在整个请求组前后采样，迁移时需要明确哪些长度和并发窗口必须各自证明 FFN FULL 执行。
- 当前脚本显式不验收优雅关闭，允许记录 forced cleanup。关闭验收必须独立落实，不能仅凭现有 passed.json 宣称 issue 完成。
- 默认 4A4F 需要 8 张 NPU，4A8F 需要 12 张且文档仍要求目标设备验证；不能直接放入现有四卡 PR gate。

单流、4A4F 的既有对照流程适合作为起点。4A8F、W8A8 和双流覆盖按实际支持范围分别验收，不自动由单流结果推导。

## 7. 现有能力的迁移边界

下表规定能力边界，不要求冻结全部配置交叉组合。具体保留、增强和候选精简见[场景矩阵附件](e2e_case_matrix.md#current-matrix)；裁剪组合需要满足该行的替代与执行条件。

| 场景或工具 | 迁移时保留什么 |
| --- | --- |
| DeepSeek-V2-Lite GPU/NPU | 各后端已有有效入口、baseline、布局、graph/DBO 与现有证据要求 |
| Qwen3 MoE | 现有 baseline、eager、graph 和 graph+DBO 验收 |
| Qwen3.6 | 当前有效场景；已撤回的 GDN DBO 不因框架迁移恢复支持承诺 |
| DSV4 CUDA | 原生/AFD 对照、多轮请求、逐窗口路径证据、Hash 新鲜性及 GSM8K |
| DSV4 NPU | 异步答案检查、同步 smoke、FFN graph、layered/DSpark 等各自明确的验收范围 |
| multi-pod | 已有布局、协调、结果验收和各 pod 的资源回收；显式保留当前证据限制 |
| 算子与部署、性能工具 | 保留仍需要的独立能力；是否纳入场景框架另按完整服务验收需要判断 |

当前 [multi_pod/runner.py](../../tests/e2e/multi_pod/runner.py) 显式关闭 MRV2 执行证据：单机 FFN marker 文件在其他 pod 不可见。已有 graph/DBO 场景由结果验收，不能据此宣称完成同等的逐 rank 路径证明。

跨 pod 窗口和证据传输属于新增能力，需要独立设计和设备验证。附件 P01–P04、P06–P07 六个 graph/DBO 场景拟增强路径证明，其余三个 eager 场景保留各自的结果验收范围。要求该证据的 Case 在不支持它的部署上应明确失败，不能由部署层静默删除检查。

删除专用 runner 的前提是其独立负载、断言、平台限制和生命周期验收已有有效去向。“已使用公共 runner”或“名称相似”不构成替代覆盖证据。

## 8. 新增、修改和删除测试的方式

| 维护工作 | 主要修改位置 | 必要判断 |
| --- | --- | --- |
| 已支持能力的新配置组合 | 仅模型场景声明、ID 清单及必要的 CI 选择和文档 | 公共模块 diff 必须为空；说明独立覆盖价值及所复用的能力 |
| 新模型 | 模型配置、场景表和 pytest 入口 | 固定模型要求、原生/AFD 对照和既有公共能力是否适用；模型差异不回写公共 runner |
| 新任务 | 对应任务模块和场景声明 | 请求流程、结果 oracle、超时和失败传播是否完整 |
| 新路径检查 | 对应检查及必要探针、场景声明 | 如何观测真实请求，哪些角色/rank/窗口必须有证据 |
| 新部署或 connector 协议 | `deployment.py` 协议表及必要环境能力、对应场景 | 启动顺序和跨 pod 协调由部署协议决定；验证就绪、布局、失败回收及 `cleanup_profile` |
| 淘汰行为 | 场景、专用辅助代码、入口、CI 和文档 | 行为是否已移除，替代场景是否覆盖同一风险 |

新增场景不展开无目的的配置笛卡尔积。已有参数化、任务、检查和部署协议能够表达时，公共模块不得改动，包含 runner、场景结构、environment、deployment、公共任务与检查、探针、multi-pod 协议及进程工具。不能以新增场景为由再加一个 case ID 分支。

确有新增任务、检查、部署协议或 connector 能力时，说明所缺能力、对应模块与验证结果，作为能力扩展评审；独立框架修复同样单列原因和验证，不算纯配置新增。关闭例外通过 `cleanup_profile` 声明，启动顺序通过 connector 协议表决定，不在模型入口重写这两项策略。

修改通过标准或删除覆盖，应说明原有结论如何保留或为何不再需要。环境缺失、平台限制和暂时失败不通过 skip/xfail 隐藏。

保留项与专项分别通过不等于完整组合覆盖等价。精简要明确接受退出的组合风险；替代项被改弱、停止执行，或出现原组合专有回归时，重新评估并按需要恢复服务场景。G02 本轮保留两卡 pure-eager 入口，G17/G37 仍按附件条件评审。

用例维护方法写入 E2E README，架构与不变量维护在模块契约。实现落地时按相关变更更新这些长期文档；本 RFC 附件记录本次基线和变更映射，持续维护的场景清单归 E2E README。

## 9. CI、插件边界与运行产物

pytest 入口、函数名和参数 ID 优先保持稳定。ready/merge、weekly 继续按明确 node ID 选择；CI 资源与场景需求匹配，不修改场景的负载或验收标准。

初期保留按模型组织的入口。新增场景不要求进入一个全局总文件，也不要求重新建设 CI。NPU CI、性能回归平台和调度平台统一作为单独的工作。

非 CI 场景按[附件的场景组维护约定](e2e_case_matrix.md#maintenance)由相关变更 PR 作者安排受影响的验证，不要求每次跑完整矩阵或将全部场景加入 CI。运行记录区分“已有定义”“完成资格验证”“本次变更已验证”，包含代码/runtime 版本、硬件、命令、生效配置、结果及产物链接；减弱的调试运行不能升级状态。稳定清单、触发规则和有效资格记录链接在迁移时进入 E2E README。

本次框架调整限于测试和文档。生产 `afd_plugin` 不依赖 E2E 代码；不因框架重组新增 vLLM/vLLM-Ascend 生产补丁。测试探针继续通过既有测试扩展接口工作。

运行输出、响应、评测结果和清理记录留在运行目录或 CI artifacts；调查日志、临时脚本和原始输出不作为项目文档提交。仓库维护可复用的运行说明、行为契约和必要设计。

## 10. 实施顺序与验收

### 10.1 分批推进

1. 以[当前场景矩阵及独立入口](e2e_case_matrix.md#current-matrix)为基线，确认逐项调整及精简前置条件，补充实际调用者和每批迁移去向。
2. 用 DeepSeek-V2-Lite baseline、eager DP2、graph DP2、graph+DBO DP2 及已有 G07 graph TP2 做迁移试点，落实场景入口、部署、任务与证据接口；用 #509 的 eager/FULL 对照检验多次部署组合是否仍可保持模型局部化。
3. 用 DSV4 多阶段验收和 NPU 专用生命周期检验接口，再迁移其他有效场景与 multi-pod 调用者。
4. 有效替代通过后删除旧分支、专用 harness 和失去使用者的辅助代码，更新运行与维护文档。

试点只限定首先迁移的范围，现有必需 gate 继续完整执行。实现不预定 PR 数量；每批应当可审阅、可验证，不先统一全部探针。

每批在实施 PR 中列明以下去向和退出条件，分别报告迁移、新增/增强、精简的完成状态：

| 批次 | 迁移去向 | 必需验证 | 旧入口退出条件 |
| --- | --- | --- | --- |
| V2-Lite 迁移试点 | 模型 Case、公共执行与 deployment、GSM8K/MRV2 | 收集与导入、命令/配置对照、关键失败路径、所迁移场景的真实设备结果 | 原负载、阈值、证据及清理语义均保留，调用者已迁移；G02 保留 |
| DSV4 与其他模型、NPU | 模型任务/检查及部署适配 | 对应多阶段、模型差异及 NPU 生命周期；N12 独立取得严格关闭资格 | 专有验收和 CLI 调用者有有效去向；未完成的新增场景不冒充已迁移 |
| multi-pod | 原协调层＋每 pod 部署执行器 | 受影响布局的地址、barrier、失败通知和回收；六项证据增强另验 | 进程拥有者唯一，原结果验收已替代；增强未通过时不宣称跨 pod 路径资格 |
| 候选精简 | 保留的模型 E2E＋D01 | 逐项删除门槛、有效运行记录与剩余风险接受 | 条件全部满足后才删除 G17/G37；否则保留 |

五卡 GPU、八卡 NPU 或跨 pod 资源待落实时，保留原覆盖的迁移可继续，新能力仍标待验证。若 N12 严格关闭暴露生产问题，单独记录修复；不得放宽 profile 获得完成状态，也不将生产修改隐含并入框架迁移。

### 10.2 分别验证什么

| 验证 | 检测的问题 | 证据边界 |
| --- | --- | --- |
| 收集安全 | 无模型资产及运行时依赖的 CPU 收集，加上运行时包存在时的导入链审查和对应环境收集；GPU/NPU 仅选适用 ID，无 checkpoint 读取、下载或设备运行时加载 | 不构建 Case、不启动 runner 或服务；缺少包的结果不能覆盖包存在的导入分支 |
| 受影响 node ID 收集、命令和环境对照 | 用例漏选、布局/参数/环境或评测设置变化 | 不证明数值、设备执行或服务关闭正确 |
| 既有主机进程/信号集成检查 | 启动失败、取消、超时和子进程回收回归 | 不证明设备行为 |
| 受影响的真实设备 E2E | 模型结果、真实路径、rank/窗口完整性和服务清理 | 按实际运行的后端、场景与版本报告 |
| 固定新增试点 G39／V2-Lite graph 3A2F | 在参考/目标运行、逐请求比较与证据能力具备后，组合新增增量只包含模型场景声明、ID 清单及必要 CI/文档，公共模块 diff 为空；五卡真实场景通过 | 前置任务与比较能力的扩展单独评审验证，整体混合改动不得称为纯配置新增；G07 是迁移用例 |

harness 不在 `tests/unit` 新建一套镜像测试。复用已有主机集成检查，必要的故障验证使用真实子进程或对应运行路径；生产行为新增或改变时，另按 UT 维护规范覆盖模块行为。

新增试点以迁移后具备所需能力的框架提交为对比基线，检查 G39 的完整增量，不能只检查 runner 一个文件。G39 使用原生参考及 3A2F graph 目标的逐请求比较，具体输入和判定见附件。所需任务或检查尚不可用时，先明确进行能力扩展并验证，不能把混合修改报告为“公共模块零改动”。该五卡任务的资源另行落实，不扩入现有四卡 PR gate，也不另外添加只验证框架方便性的长期用例。

57 项是有效服务场景口径，不是原始 collect 数量。当前 Lite 的 DeepEP 参数化入口未过滤 NPU 后端；迁移时排除这类无效 ID，须说明选择变化，不记为删除有效覆盖。

关键失败路径在现有主机集成检查或最少的真实子进程路径中验证，不围绕数据类和内部 helper 建镜像 UT：

| 验证的失败 | 必须观察的结果 |
| --- | --- |
| 必需 rank 缺失或检查未完成 | 整体失败 |
| 后一阶段收到前一阶段的证据 | 当前阶段不能通过 |
| 部分服务启动失败 | 回收已创建资源，保留启动失败原因 |
| 任务失败且清理也失败 | 保留两个原因，最终失败 |
| 双部署的任一子运行失败 | 整个 pytest node ID 失败 |

这些主机验证只证明框架拒绝错误结果和回收的行为，不代替 graph、DBO 或通信的设备证据。任务失败后的短超时尽力取证可后续改进，不阻塞试点；取证不能覆盖原始失败或拖延清理。

迁移验收必须确认：

- 必需场景仍可选择，既有部署、负载、阈值和检查没有遗漏。
- 结果检查与路径证据都在对应阶段生效，缺少必需证据时失败。
- 失败和取消后只清理本次拥有的资源；清理失败不能报告通过。
- 使用已有能力新增场景，公共模块 diff 为空；能力扩展仅修改对应模块并附实际验证。
- 设备结果、主机结果、跳过与未运行分别报告，不以收集或静态对照替代设备验收。

## 11. 参考设计及取舍

主要参考 vLLM-Ascend `18a1bd414b6609281c950206afa99aa8ac38227a`：

- [E2E 用例维护说明](https://github.com/vllm-project/vllm-ascend/blob/18a1bd414b6609281c950206afa99aa8ac38227a/tests/e2e/cases/E2E_TEST_CASE_GUIDE.md)：区分用例、公共执行和 CI 选择；支持 YAML 驱动与自定义 pytest；新增 handler 或生命周期变化属于框架改动。
- [单节点配置解析](https://github.com/vllm-project/vllm-ascend/blob/18a1bd414b6609281c950206afa99aa8ac38227a/tests/e2e/common/single_node/single_node_config.py)与[公共入口](https://github.com/vllm-project/vllm-ascend/blob/18a1bd414b6609281c950206afa99aa8ac38227a/tests/e2e/common/single_node/test_single_node.py)：配置对象参数化执行，handler 负责具体请求和断言，AISBench 执行配置的评测任务。

AFD 借鉴这些职责边界，以 Python 声明替代 YAML。独立 Case、部署模块和路径检查是 AFD 的提案，不是参考项目已有的同名架构。参考实现中的具体分支、未知 handler 仅告警及清理政策不直接移植为 AFD 的 gate 语义。

补充参考 vLLM `db914cad5bac261dbcd7cf05ded573c1d704f650` 的 [RemoteVLLMServer / RemoteOpenAIServer](https://github.com/vllm-project/vllm/blob/db914cad5bac261dbcd7cf05ded573c1d704f650/tests/utils.py)：复用服务管理边界，结合 AFD 多角色和既有清理协议落实。

上述固定版本用于研究组织方式，不等于 AFD 当前固定依赖的接口版本。

## 12. 仍需在试点中落实的设计细节

已确定的方向是 Python 场景声明、公共服务管理、按阶段验收和保留有效覆盖。试点需要落实以下接口细节，不改变这些目标：

- Case、阶段结果和检查之间的具体类型，以及跨窗口证据的传递方式。
- 旧 CLI 与模型场景入口的迁移批次，包含专用 runner 和 multi-pod 的现有调用者。
- 每批可取得的设备验证范围与退出旧实现的条件。
- 矩阵中五卡 GPU、八卡 NPU 等新增专项的资源与频率，以及 D01 替代任务的实际调度资源和实施记录；其执行责任按附件中的 PR 作者归属落实。

这些事项决定实现细节与批次，不应成为提前增加全局注册机制、通用插件体系或新调度层的理由。
